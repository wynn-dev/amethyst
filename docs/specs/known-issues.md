# Known Issues in the Reference Launcher (XMCL) — Lessons for Amethyst

This document catalogues bugs reported against the reference launcher, X Minecraft Launcher (XMCL, GitHub `Voxelum/x-minecraft-launcher`), and turns each one into a concrete design or test requirement for Amethyst. Amethyst is an Electron + React launcher for macOS 13+ on Apple Silicon only, so macOS-specific findings come first. Bugs that only affect other platforms are kept only when the underlying design flaw would also hurt us (for example non-atomic writes or non-idempotent linking).

Clean-room note: everything here is prose. Root causes come from issue threads, maintainer triage comments, and a read-only look at the reference source. Where a cause is inferred rather than confirmed, the entry says so. No original code is reproduced.

How to read an entry: the issue numbers (linked), the state (open/closed on GitHub at sweep time; "closed" does not always mean fixed), the **Symptom**, the **Root cause** (confirmed, inferred, or unknown), and the **Lesson** for Amethyst. Duplicates and close relatives are merged into one entry.

---

## Top cross-cutting lessons

1. **Pick the CPU architecture from the hardware and the chosen JVM, not from the launcher process.** The reference picks both its Java download and its LWJGL native replacement from the Electron process's own arch. Under Rosetta, or with mismatched download links, that reports x64 on an M-series Mac, so users get Intel Java and broken natives. Amethyst must detect the real host arch (including the Rosetta-translation flag), refuse to run translated, and pick natives from the selected Java runtime's own `os.arch`.
2. **Handle all Minecraft version numbers in one place, with tests.** The year-based 26.x scheme broke mod filtering (26.1 shown as 1.21.11), NeoForge listing, and any "minor version < 19" logic, which treats 26.1 as legacy. Every version comparison must go through a single comparator, tested on old alpha/beta ids, 1.x releases, snapshots, pre-releases/RCs, and 26.x ids.
3. **Never save a downloaded file that has not been checked.** Several bugs came from storing zero-byte bodies or HTML error pages as libraries, JREs, or catalogs. The SHA-1 of an empty file shows up again and again in failure logs. Download to a temp file, check size and hash, then atomically rename into place. A cached catalog must be checked against a schema and fall back to a bundled copy if it fails.
4. **Write settings and instance files atomically, and never silently reset them to defaults.** Settings reverting to defaults, an emptied instance.json that hid an instance, and Java/memory/resolution choices that snap back all appear many times. Use write-temp-then-rename, keep a last-known-good backup, validate on read, and on a parse error preserve the user's file rather than replacing it.
5. **Destructive operations must be planned, confirmed, and reversible.** Modpack updates deleted files the user had deselected. Mod updates deleted or duplicated jars. Instance deletion left files behind or created stray folders. Every destructive operation should first compute a diff plan, show it, then apply it. On macOS, deleted user content goes to the Trash.
6. **Give each mod one identity, keyed by content hash, across CurseForge and Modrinth.** Treating the CurseForge and Modrinth copies of a mod as different mods caused duplicates, false "outdated" flags, wrong-project attribution, and update loops. An update must atomically replace the old file, not add a new one next to it.
7. **Isolate accounts strictly.** Cached Xbox/Minecraft tokens were reused for the wrong Microsoft account, merging or breaking multi-account setups. Key every token by account id, check the profile id after each refresh, store secrets in the macOS Keychain, and map XErr/OAuth codes to plain, actionable messages with backoff on HTTP 429.
8. **Keep the launch path short, isolated, and observable.** Launch was blocked by scanning unrelated folders (1,000 schematics) and by one instance's loading state spilling into another. It hung forever with no log, and child stdout pipes could fill up and freeze the game. Launch must not wait on non-essential scans. Each stage needs a timeout and a clear error. The game's stdout and stderr must always be read, whether or not the log view is open.
9. **Links must be idempotent, and sharing must be opt-in.** Relinking a correct link raised EEXIST storms. Shared resource/shader folders mixed up content between instances and picked up game-written config files. Before creating a link, check whether it already points to the right place. Make sharing an explicit per-category choice, and never treat config files as content.
10. **Scanning and indexing must never loop or block the UI.** A single bad jar caused endless re-parse loops and errors. SQLite "locked/closed/missing table" retry storms produced thousands of events. Opening the saves page could freeze the window. Remember parse failures by file hash, run scans in a bounded worker pool, and treat caches as disposable: on corruption, delete and rebuild.
11. **Integrate properly with macOS.** That means Developer ID signing plus notarization (unsigned builds were reported as "damaged"), Info.plist usage strings and entitlements for microphone and Local Network (voice-chat mods, LAN play), keeping content clear of the traffic-light buttons, a theme that truly follows the system, a clean quit on Cmd+Q, and a strict energy budget (macOS 26 users saw high GPU use and battery drain).
12. **Smoke-test the packaged app, not just dev builds.** Bugs that only appeared in production builds include a missing wasm file inside the asar, a JS API used that the bundled runtime lacked (crash on start), native modules built for the wrong arch or ABI, and a blank first window. CI must build the signed arm64 app, launch it, and complete a real install and launch of a vanilla version.
13. **Never fail silently.** "One task succeeded" while nothing was installed, an Install button that does nothing, a mod install that fails without a message: these generated more reports than almost anything else. Every user action must end in a visible success or an actionable error, and errors must be saved into a diagnostics bundle the user can export.
14. **Sanitize file names in one place.** Colons, trailing spaces, and other reserved characters in instance or modpack names broke install, export, and the Java path. Map display names to safe folder names in a single function. On macOS, colons are also awkward because Finder shows them as slashes.
15. **Test interop formats with round-trips.** Exported mrpacks used SHA-256 instead of SHA-512, left out fileSize, or dropped mods. CurseForge exports were missing dependencies, and MultiMC/Prism imports failed. Export → import → compare round-trip tests, plus schema validation against the official specs, are required.

## 1. macOS / Apple Silicon

- **[#1377](https://github.com/Voxelum/x-minecraft-launcher/issues/1377) [#913](https://github.com/Voxelum/x-minecraft-launcher/issues/913)** — State: closed. **Symptom:** On an Apple Silicon Mac every Java the launcher downloaded was Intel (x64). Separately, the website's arm64 and x64 DMG links were swapped about half the time, so ARM users installed the x64 build. **Root cause:** Inferred from the reference source: Java runtime selection (Mojang manifest key and Zulu fallback) uses the Electron process arch. An x64 launcher under Rosetta therefore picks `mac-os` instead of `mac-os-arm64`. The swapped links made this happen often. **Lesson:** Ship arm64 only. At startup, detect Rosetta translation and show a blocking "wrong build" message. Pick JREs from the real hardware arch, and record each managed JRE's arch in its metadata so a mismatched JRE is flagged in the UI.

- **[#441](https://github.com/Voxelum/x-minecraft-launcher/issues/441) [#264](https://github.com/Voxelum/x-minecraft-launcher/issues/264) [#374](https://github.com/Voxelum/x-minecraft-launcher/issues/374) [#564](https://github.com/Voxelum/x-minecraft-launcher/issues/564) [#652](https://github.com/Voxelum/x-minecraft-launcher/issues/652) [#563](https://github.com/Voxelum/x-minecraft-launcher/issues/563)** — State: closed. **Symptom:** Early Apple Silicon support history. There was no arm64 build, then an arm64 build that showed no window (dock icon only) or could not open its database, and older Minecraft (before 1.19) crashed because LWJGL natives for arm64 macOS were missing. **Root cause:** Old versions ship x64-only LWJGL 2/3 natives. The reference added a native-replacement table for `osx-arm64`. The database failure was a native module built for the wrong arch or ABI. **Lesson:** Amethyst needs a tested native-substitution table for arm64 macOS covering every LWJGL generation (LWJGL 2 for 1.12 and older, early LWJGL 3 for 1.13–1.18). It must apply whenever the chosen JVM is arm64, whatever the Minecraft version. CI should launch at least 1.8.9, 1.12.2, 1.16.5, 1.18.2, 1.20.x, and a 26.x version on an M-series runner. All native Node modules must be built for arm64 and the Electron ABI and loaded in the smoke test.

- **[#925](https://github.com/Voxelum/x-minecraft-launcher/issues/925) [#1092](https://github.com/Voxelum/x-minecraft-launcher/issues/1092) [#858](https://github.com/Voxelum/x-minecraft-launcher/issues/858)** — State: closed. **Symptom:** On macOS 15 the app "is damaged and can't be opened", or simply won't launch. Homebrew cask distribution was blocked because the app is unsigned. Users were sent to a guide telling them to allow apps from anywhere. **Root cause:** The macOS build is not signed with a Developer ID and not notarized, so Gatekeeper quarantines it. **Lesson:** Sign with Developer ID, use the hardened runtime, notarize, and staple the DMG on every release. CI must check the result with Gatekeeper assessment and stapler validation, and test a quarantined download path. Never tell users to weaken Gatekeeper.

- **[#781](https://github.com/Voxelum/x-minecraft-launcher/issues/781)** — State: closed. **Symptom:** Simple Voice Chat reported "your launcher does not support macOS microphone permission", so voice chat could not work. **Root cause:** Under TCC, the launcher app is the "responsible process" for the Java child it spawns. Without a microphone usage description and the audio-input entitlement in the launcher's bundle, macOS never prompts and denies access. The fix added the Info.plist key. **Lesson:** Amethyst's Info.plist must include microphone (and, if needed, camera) usage strings, and the hardened-runtime entitlements must include audio-input. Test: launch a voice-chat mod from a Finder-launched, notarized build and confirm the permission prompt appears.

- **[#1765](https://github.com/Voxelum/x-minecraft-launcher/issues/1765)** — State: open. **Symptom:** On macOS (ARM), joining a LAN world fails with "No route to host" when the launcher is opened from Finder, but works when the launcher binary is run from Terminal. **Root cause:** macOS Local Network Privacy. A launcher started from Terminal inherits Terminal's Local Network permission. Started from Finder, the launcher (as responsible process) must hold the permission itself. The reference ships the usage string, but the prompt does not appear to fire, or the grant does not reach the Java child. Still open. **Lesson:** Include the Local Network usage string (and Bonjour service types if Amethyst browses). Trigger the Local Network prompt from the launcher itself at a sensible moment, such as the first LAN-related action, so the grant exists before Java needs it. Add a manual QA case: a Finder-launched app joins a LAN world on another machine. Document the System Settings path in the error help.

- **[#1212](https://github.com/Voxelum/x-minecraft-launcher/issues/1212) [#521](https://github.com/Voxelum/x-minecraft-launcher/issues/521)** — State: closed. **Symptom:** On macOS 26 (Mac mini, ARM) GPU use rose sharply whenever the launcher window was visible and returned to normal when minimized. On macOS 14 the app caused heavy battery drain even in the background. **Root cause:** Not confirmed. The likely cause is continuous compositor work (animated or video backgrounds, blur/backdrop-filter, constant re-renders) with no throttling when hidden. **Lesson:** Set an energy budget: when idle, the visible window should show close to 0% GPU and "Low" Energy Impact in Activity Monitor, and stop all animation timers when hidden or occluded. Avoid full-window backdrop blur and video backgrounds by default. Add a performance test that measures idle CPU/GPU for 60 s.

- **[#951](https://github.com/Voxelum/x-minecraft-launcher/issues/951) [#1144](https://github.com/Voxelum/x-minecraft-launcher/issues/1144)** — State: closed. **Symptom (macOS):** Page content overlapped the traffic-light buttons. One page took over the title bar so the window could not be dragged. "Follow system" theme showed dark while the system was light. Text overlapped at small window sizes. Too many slow transitions. Settings were also stored in a hidden `~/Library/Preferences/xmcl.plist` the docs did not mention, so a "clean reset" was impossible. **Root cause:** A frameless window without a consistent safe area or drag region, wrong mapping of the system theme, and an undocumented storage location (Electron/Chromium preferences). **Lesson:** Use a hidden-inset title bar with a single layout primitive that reserves traffic-light space on every route and defines drag/no-drag regions. Theme "System" must follow the macOS appearance live. Set a minimum window size and run layout tests at that size. Document every on-disk location, and provide a "Reset Amethyst" action that removes all of them. Keep transitions at or under ~150 ms and skip them when the system's reduce-motion setting is on.

- **[#469](https://github.com/Voxelum/x-minecraft-launcher/issues/469)** — State: closed. **Symptom:** Quitting with Cmd+Q on an M1 shows "quit unexpectedly". **Root cause:** Unknown. A crash during teardown, likely workers or native handles closed out of order. **Lesson:** Make shutdown orderly: stop tasks, flush and close the databases, terminate workers, then exit. Add a test that quits with active downloads and an open DB and checks that no crash report is produced.

- **[#135](https://github.com/Voxelum/x-minecraft-launcher/issues/135) [#232](https://github.com/Voxelum/x-minecraft-launcher/issues/232) [#17](https://github.com/Voxelum/x-minecraft-launcher/issues/17)** — State: closed. **Symptom:** Early macOS builds showed a blank window with devtools open, or got stuck on step 3 of first-run setup (choosing the data directory). **Root cause:** Production-only startup errors and a setup step waiting on a call that never returned. **Lesson:** First-run must work with no network and an empty home directory. Every step needs a timeout and an error state, and an E2E test should run on a fresh macOS user account.

- **[#1576](https://github.com/Voxelum/x-minecraft-launcher/issues/1576)** — State: closed. **Symptom:** On macOS, installing any version failed with ENOENT for an llhttp wasm file inside app.asar. **Root cause:** Confirmed in the thread: a packaging regression. The HTTP library's wasm parser was extracted as a separate file that the packaged worker could not find at its runtime path. **Lesson:** Package smoke tests must run a real download inside the signed, packaged app (including from worker threads). Assets loaded by path must be checked to exist in the final bundle (asar or unpacked).

- **[#1562](https://github.com/Voxelum/x-minecraft-launcher/issues/1562)** — State: closed. **Symptom:** The launcher crashed at startup after an update, with a main-process error saying a newer JavaScript built-in is not a function. **Root cause:** Confirmed by the maintainer: a bundler upgrade with no fixed target emitted code using an API not available in the bundled Electron's runtime. The auto-updater also left a broken install. **Lesson:** Set the bundler target to exactly the bundled Electron's Node/Chromium versions. Startup smoke-test every release artifact. The updater must verify the new bundle before switching and be able to roll back.

- **[#792](https://github.com/Voxelum/x-minecraft-launcher/issues/792)** — State: closed. **Symptom:** On macOS, starting the local server failed with an invalid Java path, because the path had Windows' "w" (javaw) appended. **Root cause:** Platform-specific executable naming applied in the wrong place. **Lesson:** Resolve the Java executable in one function per platform. On macOS that means the `bin/java` inside the JDK/JRE's `Contents/Home`. Never apply Windows-only naming.

- **[#1734](https://github.com/Voxelum/x-minecraft-launcher/issues/1734)** — State: closed. **Symptom (Mac ARM):** With about 1,000 schematic files, the Play button spun forever, and the stuck state carried over to other instances. **Root cause:** The launch button was gated on a full resource scan of the instance, and scan state was global rather than per instance. **Lesson:** Launching must not depend on scanning optional content folders. Scan state must be per instance and cancelled when the user switches. Add a test with 5,000 files in each content folder that checks Play becomes enabled within 1 s.

- **[#966](https://github.com/Voxelum/x-minecraft-launcher/issues/966)** — State: closed. **Symptom (M3):** The user could only play the Demo world. **Root cause:** No Microsoft account with a Minecraft license was selected, so the game started in demo mode with no explanation. **Lesson:** When no licensed account is active, say so clearly before launch (offer sign-in, or explain demo mode) instead of starting demo silently.

## 2. Launch failures

- **[#967](https://github.com/Voxelum/x-minecraft-launcher/issues/967) [#1360](https://github.com/Voxelum/x-minecraft-launcher/issues/1360)** — State: closed. **Symptom:** With about 100 mods the game froze at the last loading step, and starting it detached "fixed" it (reported with the reference's library). A second report: the game froze and then crashed while exporting a Flashback video, but not under another launcher. **Root cause:** Inferred for [#967](https://github.com/Voxelum/x-minecraft-launcher/issues/967): the launcher did not keep reading the child's stdout/stderr, so the OS pipe buffer filled and the game blocked on a write. [#1360](https://github.com/Voxelum/x-minecraft-launcher/issues/1360)'s cause is unconfirmed, but the symptom fits the same pattern. **Lesson:** Always drain the game's stdout and stderr into a bounded ring buffer and a log file, even when no log view is open. Add a stress test where a child process writes 100 MB to stdout and must not block.

- **[#1710](https://github.com/Voxelum/x-minecraft-launcher/issues/1710) [#1706](https://github.com/Voxelum/x-minecraft-launcher/issues/1706) [#1004](https://github.com/Voxelum/x-minecraft-launcher/issues/1004) [#1796](https://github.com/Voxelum/x-minecraft-launcher/issues/1796)** — State: closed. **Symptom:** Pressing Launch shows an empty or grey progress bar that never moves, with no logs, sometimes stuck on "refreshing user token". NeoForge 1.21.1 failed with no log output. Launching gets slower over time. **Root cause:** Unknown per issue (some came down to environment variables). The common thread is a launch pipeline with no stage timeouts and no surfaced errors. **Lesson:** Model launch as named stages (auth refresh, file check, Java check, natives, spawn, first log line), each with a timeout and a specific error. Record per-stage timings in the diagnostics bundle so "slow over time" can be measured.

- **[#588](https://github.com/Voxelum/x-minecraft-launcher/issues/588) [#302](https://github.com/Voxelum/x-minecraft-launcher/issues/302) [#724](https://github.com/Voxelum/x-minecraft-launcher/issues/724) [#764](https://github.com/Voxelum/x-minecraft-launcher/issues/764)** — State: closed. **Symptom:** GLFW or LWJGL failed to initialise ("native lib not decompressed", "platform/architecture mismatch", "Failed to initialize GLFW"). **Root cause:** Confirmed for [#588](https://github.com/Voxelum/x-minecraft-launcher/issues/588): a bug in extracting natives into the per-version natives folder. The others had natives for the wrong arch on the classpath. **Lesson:** Extract natives into a fresh per-launch (or per-version-and-arch) folder after validating the hashes. Check that the natives' arch matches the JVM's arch before spawning, and show a clear error if it does not.

- **[#731](https://github.com/Voxelum/x-minecraft-launcher/issues/731) [#756](https://github.com/Voxelum/x-minecraft-launcher/issues/756) [#1055](https://github.com/Voxelum/x-minecraft-launcher/issues/1055) [#397](https://github.com/Voxelum/x-minecraft-launcher/issues/397)** — State: closed. **Symptom:** "Unrecognized option: -p" when starting the JVM, launches failing until the user changed Java, 1.17+ never launching, and Forge for 1.7/1.8 failing because it needs Java 8. **Root cause:** The chosen JVM's major version did not fit the game's or loader's requirement. - **[#840](https://github.com/Voxelum/x-minecraft-launcher/issues/840)** — State: closed. **Symptom:** One modpack would not launch: "invalid java path". **Root cause:** Confirmed: the instance name ended with a space, which broke the path. **Lesson:** Instance folder names come from a sanitizer (trim, collapse whitespace, remove reserved characters). Display names stay separate from folder names.

- **[#857](https://github.com/Voxelum/x-minecraft-launcher/issues/857) [#865](https://github.com/Voxelum/x-minecraft-launcher/issues/865) [#910](https://github.com/Voxelum/x-minecraft-launcher/issues/910)** — State: closed. **Symptom:** A "prepend command" with several words (for example a wrapper plus a flag), environment assignments, or shell syntax broke launch. **Root cause:** The setting was treated as a single executable token. **Lesson:** If Amethyst offers wrapper commands, provide separate fields for environment variables and a wrapper argv list (parsed with documented quoting rules), and show a preview of the final command line. - **[#584](https://github.com/Voxelum/x-minecraft-launcher/issues/584)** — State: closed. **Symptom:** With OptiFine enabled, launching 1.14.4 actually started 1.12.1. **Root cause:** Version-id collision while resolving the OptiFine-patched version. ## 3. Install failures (Forge / NeoForge / Fabric / Quilt / OptiFine / vanilla)

- **[#1261](https://github.com/Voxelum/x-minecraft-launcher/issues/1261) [#1487](https://github.com/Voxelum/x-minecraft-launcher/issues/1487) [#1409](https://github.com/Voxelum/x-minecraft-launcher/issues/1409) [#801](https://github.com/Voxelum/x-minecraft-launcher/issues/801) [#528](https://github.com/Voxelum/x-minecraft-launcher/issues/528)** — State: closed. **Symptom:** Creating a NeoForge 1.21.1 instance produced 1.21.11. NeoForge for 26.1.2 was "not supported" or not listed (betas missing). The NeoForge version list was mis-sorted with old builds marked latest. NeoForge was once downloaded from the Forge repository. **Root cause:** NeoForge versions are matched to Minecraft versions by string prefix, which breaks on the 26.x scheme and on betas. Sorting was lexical. The 1.21.1/1.21.11 mix-up is suspected to be a selection/prefix bug (not confirmed). **Lesson:** Parse NeoForge versions structurally: legacy `20.x` style versus 26.x style, with beta/pre suffixes. Sort semantically, include betas behind a toggle, and test 1.21.1 versus 1.21.11 and 26.1 versus 26.1.2 explicitly.

- **[#867](https://github.com/Voxelum/x-minecraft-launcher/issues/867) [#839](https://github.com/Voxelum/x-minecraft-launcher/issues/839) [#666](https://github.com/Voxelum/x-minecraft-launcher/issues/666)** — State: closed. **Symptom:** NeoForge post-processing failed because the vanilla client jar was missing. NeoForge dependency libraries were not downloaded. CurseForge NeoForge modpacks installed without the loader. **Root cause:** Install steps ran out of order (vanilla jar not guaranteed before processors). The library list was incomplete. The CurseForge manifest's loader id was not mapped to NeoForge. **Lesson:** Run installs as a dependency graph (vanilla version JSON → client jar → libraries → loader installer → processors), each step verified. Map modloader ids from CurseForge/Modrinth manifests, including NeoForge, with tests.

- **[#685](https://github.com/Voxelum/x-minecraft-launcher/issues/685) [#730](https://github.com/Voxelum/x-minecraft-launcher/issues/730) [#1460](https://github.com/Voxelum/x-minecraft-launcher/issues/1460) [#1537](https://github.com/Voxelum/x-minecraft-launcher/issues/1537) [#1457](https://github.com/Voxelum/x-minecraft-launcher/issues/1457)** — State: closed. **Symptom:** Forge install stuck at "0.00 kb / 0.03 kb" during post-processing, PostProcessFailedError, "could not delete intermediate jar", and an ENOENT on a temporary install-profile file. **Root cause:** Confirmed in telemetry triage: the processor JVM failed (IO, checksum, classpath, or old Gson with JDK locale problems), a fast-path processor runner fell back to the slow path, and a file watcher touched temporary files while they were being written. **Lesson:** Run the processors with the loader's required Java, show live processor output in the task UI, give each processor a timeout, and record the failing processor and its outputs. ## 12. Defects inferred from the reference source (no issue found)

These came out of the code-level review behind `performance.md`. No matching GitHub issue was found, but each is a plausible hidden cause of the reported symptoms listed. Each entry is a hypothesis to guard against with a test, not a confirmed report.

- **(inferred) Java architecture mislabelled on Apple Silicon.** **Symptom:** arm64 JDKs could be recorded as x64, so arch checks, native selection, or "wrong Java" warnings misfire. **Root cause:** The reference's JVM probe reports the JVM *data model* (32/64), and the launcher maps "64" to x64. It never reads the JVM's real `os.arch`. **Lesson:** Read the arch from the runtime's `release` file (OS_ARCH) or the Mach-O header of `bin/java`, and store `arm64`/`x86_64` explicitly. Test with Temurin arm64, Zulu arm64, and an x64 JDK under Rosetta.

- **(inferred) Re-downloading truncates a good file before the new one is verified.** **Symptom:** An interrupted repair or update leaves a library, jar, or JRE file empty or partial at its real path, so the next launch fails ("zip END header not found", checksum failures). **Root cause:** The download engine opens the final destination with truncation, writes chunks in place, and deletes the file on failure. There is no temp file and no atomic rename. **Lesson:** Download to a `.part` file in the same directory, hash while streaming, verify, then rename. Never touch the existing file until the replacement is verified.

- **(inferred) A worker crash hangs the UI forever.** **Symptom:** Endless spinners on mod lists, imports, or "Play" after hashing or parsing a huge or malformed file. **Root cause:** The worker proxy only listens for messages. It has no `error` or `exit` handling, so if the worker dies (OOM from reading whole files, a native fault), every pending request stays unresolved. **Lesson:** Supervise the pool, reject in-flight jobs with a typed error, restart the worker, and add per-job timeouts. Test by killing a worker mid-job.

- **(inferred) Stale resource-index rows are never cleaned during revalidation.** **Symptom:** The resource DB keeps rows for files deleted long ago (see the SQLite entry in section 9), and lookups by inode can bind a new file to an old file's metadata. **Root cause:** Revalidation filters snapshot rows by an *absolute* directory prefix, but the rows store paths *relative* to the data root, so that branch never matches. Only inode matches are found. **Lesson:** Store relative directory and file name as separate indexed columns, and garbage-collect missing files in the same transaction as the scan. Add a test for delete-then-rescan.

- **(inferred) instance.json writes are unserialised and non-atomic.** **Symptom:** An emptied or truncated instance.json after quick successive edits or a crash (matches #1345). **Root cause:** Every instance edit triggers an independent full-file write, with no write queue and no temp-plus-rename. Two edits close together can interleave, and a kill mid-write truncates the file. **Lesson:** Use one serialised writer per file (latest-wins coalescing), atomic rename, and a `.bak` of the last good copy.

- **(inferred) TLS certificate verification is disabled for all launcher downloads.** **Symptom:** None visible. This is a silent security hole that also makes hash-less downloads (some catalogs, metadata) spoofable. **Root cause:** The HTTP connector is configured to accept any certificate. **Lesson:** Keep verification on. If a corporate proxy needs a custom CA, trust the macOS system keychain (Electron `net` does this) rather than turning verification off.

- **(inferred) The renderer reloads itself on any TypeError.** **Symptom:** The window flashes back to the splash screen, loses in-progress dialogs or forms, and can loop. Some "stuck on logo" or "blank window" reports (#1470, #1127) may be this loop. **Root cause:** The global UI error and warning handlers reload the page whenever the message contains "TypeError". **Lesson:** Use route-level error boundaries with a manual "reload view" action, and never reload automatically.

- **(inferred) Unbounded memory during long game sessions.** **Symptom:** Launcher memory grows for as long as the game runs, especially with chatty modpacks. **Root cause:** The launch pipeline keeps every stderr line and one pending promise per output chunk until the game exits, and decodes each chunk through a worker round trip. **Lesson:** Use a bounded ring buffer for game output, a streaming decoder, and post-exit crash analysis from the on-disk logs. Soak-test with a 30-minute chatty process.

- **(inferred) First paint blocked by a remote-config fetch.** **Symptom:** On first run, or after clearing caches, the window shows the splash for up to about 2 s longer on slow or offline networks. **Root cause:** The UI HTML loads a blocking script whose response waits for a feature-flag fetch with a 2 s timeout. **Lesson:** Ship built-in defaults, apply cached values synchronously, and refresh in the background.

- **(inferred, verify) Standard macOS editing shortcuts may not work.** **Symptom:** Cmd+C, Cmd+V, Cmd+A, and Cmd+Z may do nothing in text fields such as server addresses, JVM args, and search. **Root cause:** The reference sets the application menu to null on every platform. On macOS, Electron's built-in editing shortcuts come from the Edit menu roles. **Lesson:** Build a native macOS menu from roles (App, Edit, View, Window, Help), and add an E2E test that copies and pastes in a text field.
